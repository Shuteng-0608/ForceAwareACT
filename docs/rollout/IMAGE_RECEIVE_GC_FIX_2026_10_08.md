## 修复方式

新增 `StaticGraphGCGuard`：

1. 模型加载和 CUDA 预热完成后，在**相机启动及任何机器人连接之前**主动 `gc.collect()` 一次。
2. `gc.freeze()` 将此时已存在的初始化对象放入永久代，后续回收跳过这批对象。自动回收保持原有启用状态和阈值，新运行对象仍正常回收。机制见 [Python 3.10 官方 GC 文档](https://docs.python.org/3.10/library/gc.html#gc.freeze)。
3. 接收线程和会话结束后移除自己的监测回调并 `gc.unfreeze()`，恢复对象的回收范围。若进程本来已有冻结对象，启动会拒绝覆盖其他调用者的策略。
4. 记录各代回收计数、最大耗时和最多 32 条最近事件，写入运行报告 `realtime_gc`。

`run_contact_controller.py` 在启用运行的初始化/清理阶段调用该守卫；默认预览路径仍不启动设备。相机事件增加 `frame_number`、`device_timestamp_ms`、`timestamp_domain`、`available_ns`、`published_ns`；控制进程事件增加 `consumed_ns`，便于后续区分供帧与 IPC 延迟。

图像新鲜度门槛仍为 **100 ms**，推理仍为 **50 Hz**，执行仍为 **100 Hz**。模型、图像输入处理、数据时间规则、动作 `[100,7]` 和执行目标 `[7]` 均未改动。速度/加速度、刚度、力矩、首动作误差 0.05 rad、后续误差 0.05 rad、单步 0.03 rad 均保留；配置 base、操作者会话配置与传输 `.so` 的 SHA256 在 v9/v10 间相同。

## 修复验证

| 只读测试 | 时长 | D455 最大间隔 | D405 最大间隔 | 最大预测锚点间隔 | 第 2 代 GC |
|---|---:|---:|---:|---:|---|
| 原逻辑 | 45 s | 98.687 ms | 93.646 ms | 80 ms | 自动一次，66.108 ms |
| 初步冻结对照 | 45 s | 34.793 ms | 34.875 ms | 20 ms | 无自动全代回收 |
| v10 守卫验证 | 60 s | 35.139 ms | 36.013 ms | 20 ms | 20/40 s 主动探针两次，最大 0.779 ms |
| v10 最终初始化顺序 | 60 s | **34.982 ms** | **35.601 ms** | **20 ms** | 20/40 s 主动探针两次，最大 **0.924 ms** |

主动回收探针只在无机器人连接的诊断进程中执行，用于确认不是把昂贵回收简单延后。两次 API 调用总耗时约 0.935 / 0.822 ms；相机和预测没有因此产生长间隔。生产入口没有定时主动回收探针。

最终六十秒产生 **2998 次有效预测**；起始缓冲等待跳过两个网格位置，有效预测之间全部相隔 20 ms。没有超过 50 ms 的图像接收间隔，两个输入队列无报错，关节模拟输入最大接收延迟约 1.237 ms，预测 IPC 发布至消费最大约 1.185 ms。测试结束后 GC 守卫 inactive，自动 GC 仍启用。

最终测试将预回收/冻结移到相机及模拟反馈进程启动之前，与正式部署入口顺序一致。早期实验在模拟反馈进程已经启动后才预回收，导致初始队列延迟约 52–59 ms；这些启动样本保留，不能误判为修复后稳态延迟。最终顺序的接收延迟没有复现该启动积压。

CUDA 保留内存约 590 MiB，十秒以后采样的已分配内存约 413 MiB，未见持续增长；主机 RSS 的少量增长包含诊断日志列表。六十秒观测不能证明无限期运行没有内存增长，但覆盖了当前 CLI 最长 180 秒任务范围内本次最早发生的 GC 风险时段，并直接检查了两次全代回收。

离线相关 **91 项检查通过**，包含 GC 策略恢复、已有冻结状态拒绝、有限事件记录、只读诊断统计、配置指纹、会话、影子执行和传输验证。新 PC 默认入口预览确认 `hardware_connected=false`、`commands_sent=false`；v10 源码与配置指纹已核对。
